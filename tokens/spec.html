Seven of these were text-[Npx] literals inside this package's own components until 1.7.0 — 27 of them, across 8 components, at 9 sizes that appeared nowhere in tokens.css. App code has been forbidden from writing a raw size since 1.0.0; the package was doing it, which meant a consumer could not name them, override them, or be linted against them. No rendered pixel changed here. Whether 10.5 and 11 should be one size is a real argument and a visual change; it does not belong in the same pass as a rename.

Two sizes for one element, on purpose. --font-size-ribbon-h1 (24px) is the headline of a painted band, sized against the band. --font-size-h1 (20px) is the h1 of a page with no ribbon at all — sign-in and the kiosk, which is exactly where its single consumer lives. Before 1.7.0 the ribbon hard-coded 24px, so the system's stated "h1 size" was a size that 95% of its h1s did not use.

1.8.0 — the tier that stopped short. Everything from kpi down is desk density: a number on a card, on a machine at arm's length. A kiosk is a different surface, and the first consuming app proved it by refusing the scale rather than bending it — its wall clock and its punch confirmation were both raw literals, because 25px on a tablet bolted to a wall is a number an operator crossing the room cannot read. glance (64) and glance-sm (28) are those two sizes, named for the reading condition rather than the device so a wall board or a shift-change display can reach for them too. Neither declares line-height: the two literals carry different leading at their only call sites, so a token value would be wrong at one of them.

1.8.0 — ribbon-meta is now body-sm. 12.5px was named in 1.4.0 after the first three places it appeared, which were the ribbon's subtitle and its buttons. It is the most-used size in the consuming app — 115 sites across 19 files — and none of those 19 files renders a Ribbon. Inside this package only 2 of 10 uses are the ribbon; on this page, only 4 of 22. The old spelling stays live as a deprecated alias in tokens.css and both Tailwind ports, removable in 2.0.0. Same 12.5px, same 1.35 leading: a rename must not resize.

One prop across the control family — Button, Chip, Select, DateField, FormField — so a tap-sized form is coherent rather than one raised control beside four default ones. Never raise --control-height to get here: that resizes every control in every E911 app.

Boolean controls Checkbox · Radio — box is --check-size, target is --tap-target

Checkbox — every state, size="md"
Radio — the same box, drawn round

The label is INSIDE the control, so the whole row toggles it and the row is --tap-target tall at both sizes. The box is --check-size (18px) / --check-size-tap (24px) — a hit area larger than the painted box is the point, not an oversight. A wrapping label like this is also the accessible name, which is why these do not go inside FormField: that renders a label ABOVE a control, and a checkbox's label sits after the box and has to be part of the target.

Unchecked, the box is --surface-card with a --border-control stroke — 3.38:1 light / 3.27:1 dark on a card, the same 1.4.11 floor an input's boundary is held to, because a checkbox is the one control whose entire meaning is non-text. Checked, it is an --action-primary fill (4.62:1 / 5.01:1 against the card) carrying a --text-on-action mark (4.62:1 / 5.41:1 against the fill). Every one of those figures is in npm run audit:contrast.

Status tones five since 1.7.0 — pill + dot + word, always

The five, at the same geometry
Approved Missing punch Rejected Live estimate Voluntary

Squint at that column, or step back from the screen. Relative luminance of the five light-mode fills: info 0.1104 · bad 0.1125 · ok 0.1132 · neutral 0.1135 · warn 0.1280 — a 0.018 spread, three of them inside 0.001 of each other. Each clears 4.5:1 on its own fill (5.14–5.58), which is all AA asks and all it asks: to a dichromat, or across a dim room, these are five shades of one grey. The word is the channel that survives that. Going from three tones to five doubles down on it rather than diluting it.

Why the system stopped at three, and why it stopped stopping

The three-tone rule had a good argument behind it — a status with no tone is a status the reader has to interpret — and it was refused several times before this. The census that overturned it, from the first consuming app: warn was used 84 times across ~60 distinct labels, and about 17 were cautionary. The rest were classification ("Note", "Net", "Moves money", "Eligible", "Live estimate") and plain absence ("No timesheet", "Not configured", "No roster for this date"). Gold meant needs attention and pay is not in question on the same screen. The two new tones give the amber back its meaning; they do not let a status avoid having one.

When neutral is legitimate. A state that is real, known, and carries no judgement — a classification the operator should read but need not act on. It is not the tone for "I could not decide". The test: if the label reads exactly the same with no pill at all, the answer is no pill, not a neutral one.

Disabled & selected tokens since 1.7.0, not each component's own opacity

Disabled

Before 1.7.0 there was no token, so Button, Select and DateField each chose their own opacity or their own grey and nothing compared them — the same drift that produced the 2.01:1 ribbon label. WCAG 1.4.3 exempts a disabled control from the contrast floor, and the audit records these as kind:"disabled" rather than failing them. That exemption is permission to be quiet, not permission to be unreadable: a dispatcher still has to read WHICH action is unavailable to know what to do instead. The honest figure, not the flattering one: --text-disabled is 3.38:1 on --surface-card, but 2.90:1 light / 3.23:1 dark on --surface-disabled — which is where a disabled Button's label actually sits. If a later change makes disabled text quieter, 2.90 is the number to argue against. The boundary is deliberately fainter still (1.33–1.55 light): the fill and the label already say "unavailable", and a border held to 3:1 would make the disabled control the loudest object in the form.

Three states that look adjacent and are not. --surface-tint is a POINTER resting somewhere; --surface-brand-soft is the active nav DESTINATION, a statement about where you are; --surface-selected is what the operator CHOSE. Select's option list and DateField's calendar used tint for all three, so hovering an unselected option made it look chosen. Selected is one step darker than tint in light and one step lighter in dark — a choice outranks a pointer, so it has to survive being hovered. Flip the theme and hover both.

The fill is not the identifier, and must not become one. --surface-selected is 1.31:1 on card in light and 1.17:1 in dark — nowhere near the 3:1 that 1.4.11 asks of a boundary identifying a component state, and raising it there would put a mid-grey bar through a table meant to be read. --border-selected carries the requirement instead: it is --action-primary, 3.53:1 light and 4.28:1 dark. Every consumer must ALSO carry the state non-visually — aria-selected or aria-current, which the list above does — and Select additionally keeps a check mark, a font-weight and --text-brand. Nobody removes that check mark on the grounds that the fill now exists: the fill is the weakest of the four signals, not the strongest.

Scroll me. scrollbar-color tints the thumb with --border-strong and leaves the track transparent. It is the STANDARD two-value property on purpose: the ::-webkit-scrollbar family can redraw the widget completely, and a redrawn scrollbar loses the platform's overlay behaviour, its touch expansion, and — on a wall tablet — its hit area. Tinting a thumb is theming; redrawing the widget is shipping a different control.

Why this is not a cosmetic pass

A dispatcher selecting a badge number to paste into the CAD got a cobalt band across a warm-neutral table — the one moment in the app that looked like an unstyled form. And --border-control was raised to 3:1 in 1.5.0 precisely because "an empty field on a wall tablet at arm's length was invisible"; a placeholder left at the browser's #9AA0A6 undoes half of that on the same field.

The base block also sets ::placeholder { opacity: 1 }, and that line is load-bearing rather than tidy: Firefox ships the pseudo-element at 0.54, which would take --text-tertiary from its audited 4.98:1 to roughly 2.6:1 — a tier raised in 1.2.0 specifically to clear 4.5:1, silently undone by a UA default in one browser.

Every value in the block is a token that already existed. It spends no new colour — it stops shipping the browser's opinion of six surfaces the system had otherwise decided everything about.

These are two states, not one. Until 1.7.0 a table still fetching and a table with nothing in it were the same rendering, so an operator on a slow link read "No exceptions" off a queue that had forty — which is why loading outranks the empty path in DataTable rather than racing it. And "No rows" is not a state, it is a shrug: an empty queue and a filter that matched nothing need opposite responses, so EmptyState says which emptiness this is. The skeleton rows are --row-height tall for the same reason — the page must not reflow under the pointer when the real rows land. The skeleton is aria-hidden and the container carries aria-busy plus an sr-only role="status": a picture of content that does not exist yet must not be announced as a table of blanks. And its pulse carries its own prefers-reduced-motion rule, which is the one case the global clamp does not cover — an INFINITE animation held at 0.01ms keeps looping and strobes instead of stopping.

DataTable owns that scroller itself, and it is focusable and named. A container that scrolls only by drag is a 2.1.1 failure: there is no keyboard gesture for "scroll the thing under the pointer" when the thing under the pointer cannot take focus. Tab to the table above and use the arrow keys. Do not wrap a DataTable in your own overflow-x-auto — that nests a second scroller, and the outer one, which is the one the pointer actually hits, is the unnamed unfocusable kind this exists to stop shipping.

Motion scoped by distance, not by importance

Hover this card
--e911-dur · 170ms
--e911-dur-slow · 240ms

Until 1.7.0 the system had two durations, and the larger of them was carrying both a chip's colour change and the rail's 64px → 224px width animation. Those are not the same movement: a colour swap reads as instant at 170ms, a 160px layout shift reads as clipped. 240ms is the top of the 150–250ms band product UI can spend before an operator mid-task starts waiting for the interface.

Reach for it when something changes size or position — the rail opening, a Dialog entering, a Select list unrolling. Everything else stays on --e911-dur, and a press or a hover stays on --e911-dur-fast (110ms). There is deliberately no separate exit duration: nothing in the system currently animates out on a path where the difference is visible, and a token with no consumer is how --font-size-h1 ended up describing a size only one page renders.

The eyebrow is a deliberate exception, and this is the record of it. An external design review flagged it in 1.7.0 against a general rule that is usually right — a kicker above a heading is decoration, and a heading that needs one is a heading that has not been written yet. It is being kept. The shell's navigation is a --rail-width (64px) icon rail with no breadcrumb, collapsed by default, so the eyebrow is the only element on the page naming which of the six E911 domains the operator is standing in. The heading says "Pay Period 14"; the eyebrow says "Approvals". That is wayfinding, and it is the wayfinding the general rule assumes a breadcrumb already provides.

It is kept on a condition, which is what makes it an exception rather than an opinion: the eyebrow must carry what the collapsed rail cannot. An eyebrow reading "APPROVALS" over a heading reading "Approvals" is the decoration the review described — and at that point the general rule is right and it should go.
